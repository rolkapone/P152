# ADR-APP-10 — Socle `core/` livré en US-003 : contrats du schéma v1, du catalogue et des garde-fous

> Index des ADR : [index.md](index.md). Découpé de l'ancien `docs/architecture.md` (contenu inchangé).


> Statut : **Accepté** (2026-10-20, revue US-003 APPROVE). Précise ADR-3D-02, ADR-APP-03/05/07/08 sans les contredire.

**Contexte.** US-003 livre le premier code de `src/core/` (schéma, catalogue, pipeline d'import) avant toute UI et toute scène. Plusieurs points laissés ouverts par les ADR doivent être fixés pour que US-004 (scène), US-005 (shell) et US-018 (persistance) s'appuient dessus sans refonte.

**Décision.**
- **Schéma `SetupV1`** (`core/schema/setupV1.ts`, Zod `jitless` via le point d'entrée unique `core/schema/zod.ts`) : conforme à ADR-3D-02, avec ces précisions :
  - `desk.materials` ajouté (surcharges par slot, comme les objets) : le bureau a lui aussi des slots (`top`, `legs`).
  - Champs de la vision long terme **présents mais fermés** en v1 : `product: null`, `environment.room: null`, `environment.lighting: "neutral"` seulement. Les ouvrir (R3, R5) sera une migration v1 → v2, pas une refonte.
  - Bornes structurelles : coordonnées ±10 000 mm (un objet peut déborder, c'est une alerte), `rotationY` dans [-360, 360], nom et libellé 1 à 80 caractères sans caractère de contrôle, ≤ 24 paramètres, ≤ 8 surcharges de matériau, ≤ 32 clés dans `extensions`, profondeur JSON ≤ 16, 50 objets.
- **`parseSetup(text, catalog, { declaredBytes })`** (`core/io`) : seule voie de lecture d'un setup (SR-01). Ordre : taille déclarée puis taille UTF-8 (≤ 1 Mio) → retrait d'un BOM UTF-8 initial (un seul) → `JSON.parse` → garde structurelle itérative (clés `__proto__`/`constructor`/`prototype`, profondeur, prototype non standard) → enveloppe et version → migrations → schéma strict → contrôles sémantiques contre le catalogue (entrée connue et du bon type, `catalogVersion`, paramètres connus et dans les bornes, enums, matériaux et slots, ids uniques, `mount` sans parent manquant ni cycle, style connu) → normalisation (paramètres absents = défauts du catalogue) → document gelé. Erreurs = `{ code, path }` : 19 codes traduits par `errors:import.<code>`, chemin assaini (segments non identifiants remplacés par `?`, 120 caractères max) ; jamais de contenu du fichier. `checkDeclaredSize(File.size)` est exposé pour refuser avant lecture.
- **Catalogue** (`core/catalog`) : `validateCatalog(files)` valide tous les fichiers de `assets/catalog` (schémas stricts, sauf les blocs descriptifs de `studio.json`), puis `min ≤ défaut ≤ max`, défauts d'enum, presets dans les bornes, `formats` alignés sur l'enum `format`, ids uniques, toutes les références (matériaux des slots et des styles, types des styles, bureau du studio) ; renvoie **toutes** les anomalies. **Plafonds GPU** (`core/catalog/limits.ts`, M-04) : ≤ 10 000 triangles et ≤ 8 draw calls par type, segments du cyclorama ≤ 64, shadow map ∈ {256…4096}, ≤ 32 échantillons de flou, budgets de scène ≤ ADR-3D-08. Ports `CatalogSource` et `SetupRepository` déclarés dans `core/ports`.
- **Catalogue embarqué hors de `core/`** : l'adapter `embeddedCatalogSource` (`persistence/catalog/embeddedCatalogSource.ts`) charge les JSON par `import.meta.glob` (un nouveau type = un fichier JSON du TA, sans code), les valide avec `validateCatalog` (une fois, mémoïsé) et les expose via le port `CatalogSource` ; `app/` l'instanciera (ADR-APP-09). Il est dans `persistence/` (adapters, ADR-APP-07) et non dans `core/`, car il dépend du bundler : `core/` reste exécutable tel quel côté serveur ou en Node. Les tests de `core/` valident le catalogue lu sur disque (`tests/unit/helpers/fixtures.ts`).
- **Frontières de couches et texte en dur** : appliquées **avec les règles natives d'ESLint et deux règles locales** (`config/eslint-plugin-p152.mjs`, sans dépendance, précisé en US-005 T0), vérifiées par un test (`tests/unit/lint-rules.test.ts`, cas positifs et négatifs pour chaque règle) :
  - `core/` (tous les fichiers `src/core/**/*.{ts,tsx,mts,cts}`) : **liste blanche** d'imports (`no-restricted-imports`) : seulement des modules relatifs de `core/` (`./x`, `../x`, `.` et `..`), `zod` uniquement dans `core/schema/zod.ts`, `vitest`/`fast-check` uniquement dans ses tests. **Chemins relatifs** : la règle locale `p152/core-relative-imports` résout le chemin depuis le fichier et exige qu'il reste dans `src/core` (les tests de `core/` peuvent aussi viser `tests/`, pour les fixtures partagées) : `from ".."` est accepté depuis `core/catalog/x.ts` et refusé depuis `core/x.ts`, quelle que soit l'écriture (`./../..`, `io/../../..`) ; elle couvre `import`, `export … from` et `export * from`. En seconde ligne, les motifs texte refusent toujours `node_modules`, les autres couches, `src/locales`, `tests/` et `src/main`. `no-restricted-syntax` interdit l'import dynamique, les types `import("x").T`, `import.meta` (pas `new.target`), `require` et le JSX (le runtime automatique importe `react/jsx-runtime` sans import visible ; `tsconfig.core.json` le refuse aussi avec `"jsx": "preserve"`, erreur TS7026 **vérifiée par une vraie compilation** : le test compile un module en mémoire de `src/core/` avec les options de `tsconfig.core.json` via l'API du compilateur, attend TS7026 pour du JSX, une erreur pour `document`, et zéro erreur pour du TypeScript pur) ; `no-restricted-globals` interdit le DOM et les E/S (dont `globalThis`, `self`, `crypto`, `process`) en complément du compilateur.
  - **Pureté vérifiée par le compilateur** : `tsconfig.core.json` (`lib: ["ES2023"]` sans DOM, `types: []`) type-check le code de production de `core/` dans `pnpm typecheck` (donc `pnpm check` et la CI) ; toute API du navigateur ou de Node y est une erreur de compilation.
  - autres couches : `no-restricted-imports` par motifs regex (ADR-APP-07).
  - texte en dur dans `ui/` et `app/` (`.ts` et `.tsx`) et dans les `.tsx` de `render/` (hors tests) : règle locale `p152/no-literal-text` sur le texte JSX (avec au moins une lettre de n'importe quelle écriture, `\p{L}`), et sur les chaînes et gabarits (`TemplateLiteral`) rendus comme enfant d'un élément ou d'un fragment ou comme valeur des attributs `alt`/`aria-label`/`aria-description`/`aria-placeholder`/`aria-roledescription`/`aria-valuetext`/`label`/`placeholder`/`title`, **y compris à travers** un ternaire (branches `consequent`/`alternate`, imbriqué ou non), une expression logique (`&&` : côté droit ; `||` et `??` : les deux côtés), une concaténation `+`, une expression d'un gabarit, `as`/`satisfies`/`!`, un tableau (`{["Hello"]}`, décomposition comprise), ce que renvoie un rappel ou une IIFE (`{xs.map(() => "Item")}`, corps expression ou `return` de premier niveau, render prop), `String("x")`, une méthode de chaîne sur un littéral (`concat`, `join`, `toUpperCase`…) et un gabarit étiqueté. **Props texte des composants** (élément à majuscule ou pointé, ex. `<Panel>`, `<Aria.Tab>`) : `body`, `caption`, `children`, `content`, `description`, `heading`, `label`, `message`, `text`, `textValue`, `title`, `tooltip`, et leurs formes préfixées (`toggleLabel`, `emptyTitle`) ; liste dans `eslint.config.js` (`COMPONENT_TEXT_PROPS`), à compléter avec chaque nouveau composant (US-005). Ne sont pas signalés : les arguments littéraux d'un appel (`t("key")`, `f("id")`), la condition d'un ternaire ou la gauche d'un `&&` (`{s === "ready" && …}`), les autres opérateurs, les autres attributs (`className={c ? "on" : "off"}`, `data-*`), les chaînes sans lettre (`" / "`, `alt=""` d'une image décorative). **Limite restante** : une constante définie ailleurs (`const M = "Hello"; … {M}`) relève de la revue.
  - **Choix (US-005 T0) : règle maison étendue plutôt que `eslint-plugin-i18next`.** La dernière version (6.1.5, publiée le 2026-06-28) a été examinée : en mode `jsx-text-only`, `no-literal-string` ignore toute chaîne dont le parent direct n'est pas un élément ou un fragment JSX (`lib/rules/no-literal-string.js`, l. 183-188), donc précisément `{c ? "Yes" : "No"}`, `{c && "Yes"}` et `{"a" + n}` : il ne remplit pas le critère dans le mode demandé ; le mode `jsx-only`, qui les verrait, signale aussi tous les attributs hors liste d'exclusion (bruit sur `name`, `variant`, `data-*`…). Il ajouterait en outre une dépendance CommonJS (`requireindex`, inchangée depuis 2022). Les sélecteurs `no-restricted-syntax` ne savent pas exprimer « atteint uniquement par des branches de valeur » à profondeur quelconque (le test d'un ternaire serait un faux positif) : d'où une règle locale d'une soixantaine de lignes, testée. `eslint-plugin-boundaries` n'est pas ajouté non plus (même raison qu'en US-003) ; à réévaluer si les règles se compliquent (ex. exceptions par fichier).
- **i18n** : `ui/i18n/config.ts` crée une instance i18next synchrone (ressources `src/locales/en/*.json` embarquées, `escapeValue: false`), clés typées par augmentation de module (`ui/i18n/i18next.d.ts`) ; `main.tsx` fournit l'instance et synchronise `<html lang>`.
- **Tests** : Vitest en deux projets (`node` pour `src/core/**` et `tests/unit/**`, `jsdom` pour le reste) ; fixtures `tests/fixtures/setups/v1/{valid,invalid,malicious}` (les fichiers malveillants sont exclus de Prettier pour rester octet pour octet) ; fuzzing fast-check de `parseSetup` (jamais d'exception, clés interdites injectées partout rejetées, aller-retour `serialize → parse` sur des setups valides générés depuis le catalogue). Seuils de couverture en cliquet sur `src/core/**` : lignes/instructions/fonctions 95 %, branches 90 % ; sur `src/persistence/**` : 90 % partout (ADR-APP-08). `src/state/**` a reçu le même seuil (90 %) avec son premier module (US-004 ; vérifié en US-005 T0). Le seuil global (80 %) sera posé avec la première UI (US-005).

**Conséquences.**
- (+) US-004 lit le bureau et le studio dans un catalogue déjà validé ; US-018 n'a plus qu'à brancher `parseSetup` sur `localStorage` et l'import de fichier.
- (+) Garde-fous de couches et d'i18n actifs dès maintenant, sans dépendance supplémentaire.
- (−) Les règles natives sont moins expressives que `eslint-plugin-boundaries` (pas de graphe de dépendances) ; un import transitif via un barrel reste possible et relève de la revue. Depuis US-005 T0, les chemins relatifs de `core/` sont contrôlés sur leur chemin résolu (`p152/core-relative-imports`) ; un `import x = require("..")` (syntaxe TypeScript `import =`) ne passe pas par cette règle mais est refusé partout par `@typescript-eslint/no-require-imports` (configuration recommandée, testé dans `tests/unit/lint-rules.test.ts`). Un `require` aliasé (`const r = require; r("x")`) n'est pas détecté non plus (sans portée pratique : `require` n'existe pas dans le bundle ESM et n'est pas typé dans `tsconfig.core.json`).
- (−) `fast-check` ajouté en dépendance de développement (4.10.2, publiée le 2026-09-19, `pnpm audit` sans vulnérabilité) : prévu par ADR-APP-08.

**Alternatives écartées.**
1. **`eslint-plugin-boundaries` + `eslint-plugin-i18next` dès US-003** : deux dépendances de plus pour des règles que l'arborescence actuelle permet d'exprimer nativement.
2. **Clamp silencieux des valeurs hors bornes à l'import** : contraire à ADR-APP-03 (l'utilisateur doit savoir ce qui a changé).
3. **Validation du catalogue seulement en test** : le catalogue embarqué est aussi validé à l'exécution (une fois, mémoïsé) ; coût négligeable et défense en profondeur si un fichier du TA est altéré.
